# 目的

Taskの担当者を、自由入力ではなく担当者マスタから選ぶようにする。表記ゆれや入力ミス（例: `sato` と `Sato`）を防ぎ、ガントの担当者絞り込みやWBSの担当者列を安定させる。

# 現状（事実）

- Taskの `owner` は自由入力の文字列である。作成ダイアログと編集ダイアログの担当者欄は、どちらも文字入力欄である。
- 既存のTask 11件で使われている担当者は次の9種類である。

  | 担当者 | 件数 |
  |---|---|
  | unassigned | 3 |
  | product-owner | 2 |
  | ai-team | 1 |
  | kobayashi | 1 |
  | sakai | 1 |
  | sato | 1 |
  | suzuki | 1 |
  | tanaka | 1 |
  | yamada | 1 |

- `unassigned` は、担当者未定を表す値として、作成時の既定値に使われている。
- 担当者を管理する仕組みは、コードにもMarkdownにもない。
- ガント画面の担当者絞り込みは、Taskに現れる値から作っている。

# 成功条件

- 担当者マスタがMarkdownファイルとして存在し、既存Taskの担当者9種類がすべて登録されている。
- 作成ダイアログと編集ダイアログの担当者欄が、マスタから選ぶ選択式になる。
- マスタにない担当者を、画面とAPIから新たに設定できない。
- 既存のTaskは、担当者の値もファイルも変更されない。
- 既存のAIチャットによるTask作成、状態変更、WBS生成、ガント、Git操作を壊さない。
- DBやUI固有の永続データを追加しない。

# 対象範囲

## 実装する

- 担当者マスタのMarkdownファイルの作成と、既存Taskの担当者9種類の登録。
- マスタを読む処理と、担当者一覧を返す `GET /api/owners`。
- 作成ダイアログと編集ダイアログの担当者欄を選択式にする。
- Task作成・更新時の担当者の検証（マスタにあるか）。
- テスト、READMEの更新。

## 実装しない

- 画面からの担当者の追加・変更・削除。マスタはMarkdownを直接編集して管理する。
- 担当者の表示名、所属、メールアドレスなど、ID以外の属性。
- 既存Taskの担当者の書き換え、表記の統一。
- ガントの担当者絞り込みの変更（現在の、Taskに現れる値から作る方式のままにする）。
- 担当者ごとの稼働や権限の管理。

# 設計判断

1. **マスタは `masters/owners.md` の1ファイルにする。** 1人1ファイルにすると、担当者の追加のたびにファイルが増え、9人でも管理が重くなる。`context/` は背景・制約などの文脈用なので使わない。Task、Requirementと同じくMarkdownを正本とし、DBは使わない。
2. **書式は、担当者IDを1行ずつ並べた箇条書きにする。** 既存のFront Matter解析は単純な値だけを扱い、複数件の一覧に向かないため、専用の小さな解析を使う。
   - `- sato` の形式の行だけを担当者として読む。それ以外の行（見出し、説明文）は無視する。
   - IDは半角英数字、`-`、`_` に限る。重複したIDは1件として扱う。
3. **Taskの `owner` には、これまでどおりIDを保存する。** 既存Taskの値とファイルを変えないため。表示名は今回持たない。
4. **`unassigned` もマスタに登録する。** 既存Taskが使っており、作成時の既定値でもあるため。マスタの先頭に置き、担当者未定を表す値として説明を添える。
5. **検証は、担当者を変更したときだけ行う。**
   - 作成時は、担当者がマスタにあることを確認する。画面からの作成（`strict`）は、ない場合に理由を示して拒否する。AIチャット経路は、ない場合に `unassigned` にする。
   - 更新時は、担当者が変更された場合だけ確認する。担当者を変えない更新（状態のドラッグ操作、本文の編集など）は、マスタにない担当者のTaskでも失敗させない。
6. **編集ダイアログでは、現在の担当者がマスタにない場合も、その値を選択肢に残す。** 「（マスタ未登録）」と付けて表示し、保存時に値が黙って書き換わらないようにする。手で編集されたTaskへの安全策である。
7. **マスタが読めない場合の動作。** ファイルがない、または担当者が1件もない場合は、作成・更新を拒否する。理由として、マスタの場所を示す。担当者欄が空になって、原因が分からなくなることを避ける。
8. **APIは `GET /api/owners` を追加する。** 担当者IDの一覧を返す。画面は、ダイアログを開くたびに取得し、マスタを編集した直後でも再読込なしで反映する。

# 実装ステップ

1. `masters/owners.md` を作成し、担当者9種類を登録する（先頭に `unassigned`）。
2. マスタを読む関数を `app/lib/markdown.js` に追加する。
3. `createTask()` と `updateTask()` に、担当者の検証を追加する（設計判断5、7）。
4. `GET /api/owners` を追加する。
5. 作成ダイアログと編集ダイアログの担当者欄を選択式にする。作成ダイアログの既定値は `unassigned` とする。
6. テストを追加する（下記）。
7. READMEに、マスタの場所、書式、担当者の追加方法を追記する。
8. 動作確認後、変更をGitコミットする。

# 検証

- **Markdown I/O**: マスタの箇条書きだけが読まれ、見出し・説明文・重複・不正な行が無視または除外される。
- **マスタの内容**: `masters/owners.md` の登録が、既存Taskの担当者9種類と過不足なく一致する。
- **API**:
  - `GET /api/owners` がマスタの一覧を返す。
  - 画面からの作成で、マスタにない担当者が400になり、ファイルが作られない。
  - 更新で、担当者を変更しない場合は、マスタにない担当者のTaskでも成功する。担当者を変更してマスタにない値にする場合は400になる。
  - マスタがない場合に、作成・更新が理由付きで失敗する。
- **既存経路**: AIチャット経由の作成で、マスタにない担当者が `unassigned` になる。既存Taskのファイルが変更されていない。
- **画面**: 作成・編集ダイアログの担当者欄がマスタの内容で選択式になる。マスタ未登録の担当者のTaskを開くと、その値が「（マスタ未登録）」付きで表示され、そのまま保存しても値が変わらない。ガント、WBS生成が引き続き動く。
- `npm test` が通る。

# リスク

- マスタに担当者を追加するには、Markdownの直接編集が必要になる。→ READMEに手順を書く。画面での管理は、利用状況を見て別のPlanで検討する。
- 手で編集されたTaskの担当者がマスタと食い違う。→ 設計判断5、6により、更新の失敗や値の書き換えを起こさない。
- 担当者名の変更（例: 退職者の整理）で、既存Taskの担当者との対応が崩れる。→ 今回の対象外。IDは変更せず、追加だけを想定する。

# 未決事項

未決事項はない。以下は決定済みである。

- 担当者の追加・変更・削除は画面から行わない。`masters/owners.md` をMarkdownで直接編集して運用する。
