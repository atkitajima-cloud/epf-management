# 目的

EPF Managementをチーム内で共同利用できるようにする。ただし、Markdown / GitをSingle Source of Truthとする原則、DBを使わない原則、各利用者のCodex認証情報を共有しない原則は維持する。

# 現状と前提

## 現状

- アプリは単一のローカル作業コピーを対象に、`127.0.0.1` で起動する。
- Taskの作成・更新はMarkdownファイルに直接書き込まれる。
- Git状態は表示のみで、commit / pull / pushはアプリから行わない。
- Codex Adapterはローカルにログイン済みのCodex CLIとユーザー設定を利用する。
- Task IDは現在の最大連番から採番するため、複数ブランチでの同時作成に衝突余地がある。

## 第一候補の運用モデル

共有Webサーバーを立てるのではなく、各メンバーが同じGitリモートをcloneし、自分のPC上でアプリを起動するローカルファースト方式とする。

```text
Git remote (Markdownの共有履歴)
       ↑ 手動 git pull / commit / push
各メンバーのclone + localhostアプリ
       └─ 各自のCodex CLI / 認証情報
```

この方式により、認証・ネットワーク公開・中央DBをPoCの範囲に持ち込まずに共同編集を開始できる。共有ホスト型Webアプリは、認証・アクセス制御・同時編集・Codex実行権限を別途設計できる段階まで対象外とする。

# 成功条件

- 新しいメンバーが手順に従ってclone、起動、CodexまたはMockの利用を開始できる。
- Markdown変更をGitで確認・同期できる。
- pull後にKanban、WBS、Git状態が正しく更新される。
- 同じTaskを並行編集した場合、上書きせず競合を検出して利用者に再読込を促せる。
- 複数メンバーがTaskを作成してもID衝突を防止または解決できる。
- Codexの認証情報、ローカル設定、生成途中の一時ファイルをリポジトリに含めない。
- DB、共有認証情報、自動commit / pushを導入しない。

# 対象範囲

## 実装する

- チーム導入ガイド、Git運用ルール、起動設定の整備
- 変更競合の検出と安全な保存
- Git同期後の再読込・変更状態の可視化
- 明示的なPullと早送り更新のみの同期
- 任意の変更後に使える明示承認付きCommit & Push
- Task ID採番の共同運用対応
- AI Adapterのチーム利用上の境界と診断表示
- CIでのMarkdown検証

> 実装状態: この文書に記載する `Commit & Push` はレビュー対象の計画であり、現行UIには未実装である。承認前にGit操作APIやボタンを追加しない。
## 実装しない

- LAN / インターネット公開された共有Webサーバー
- アプリ内ログイン、権限管理、認証情報の代理実行
- DB、WebSocketによるリアルタイム共同編集
- AI更新のたびに確認なしでcommit / push / pullすること
- チーム共通のCodexアカウント・APIキーの保管

# 設計方針

## 1. 配布とローカル起動

- READMEにclone、Node.js確認、`npm start`、`AI_ADAPTER` 切替、更新時のpull手順を記載する。
- `.env.example` を追加する場合も秘密情報を置かず、`PORT`、`AI_ADAPTER`、`CODEX_CLI_PATH` の例だけを示す。
- アプリのbind先は既定の `127.0.0.1` を維持する。LAN公開は明示的な別設計・認証実装なしでは許可しない。
- Codex CLIは各自でログインする。未導入・未認証時はMockへフォールバックし、画面に理由を出す。

## 2. Gitを共同作業の調停点にする

- 推奨フローを「手動 git pull → 編集・生成 → 内容確認 → WBS再生成 → git status確認 → 手動 git add / commit / push」とする。
- 通常のGit操作はアプリ外（CLIまたは既存Gitクライアント）で行う。アプリは状態と必要な案内を表示する。
- Git状態パネルに、任意の人間操作後にユーザーが明示的に押せる `Commit & Push` を置く。自動実行はしない。
- `Commit & Push` はヘッダーの「更新」ボタン左側に置く。変更がない場合と実行条件を満たさない場合は無効化し、理由を表示する。
- `Pull` はヘッダーの `Commit & Push` 左側に置く。操作順は「WBSを生成 → Pull → Commit & Push → 更新」とする。
- `Pull` は作業ツリーに未コミット変更やGit競合がない場合だけ有効にする。未記録の変更がある場合は、先に確認・commit・競合解消を行うよう理由を表示する。
- 同期は `git pull --ff-only` を使う。リモートの履歴をそのまま早送りできる場合だけ更新し、自動マージ、rebase、force操作は行わない。
- 実行中はボタンを無効化し、「取得中」を画面に表示する。更新なし、取得成功、早送りできない失敗、通信・認証失敗を区別して表示する。
- 取得成功後はTask一覧とGit状態を再読込する。WBSは正本ではないため自動生成せず、必要なら利用者が「WBSを生成」を押す。
- 実行前に確認ダイアログで変更ファイル一覧とcommit messageを表示する。利用者が確定した後だけ実行する。
- 実行中はボタンを無効化し、「コミット中」「送信中」を画面に表示する。二重実行を防ぐ。
- 完了時はcommitの短縮IDと送信先ブランチを成功表示し、Git状態を再読込する。失敗時はcommit前かpush時かを区別して表示する。
- pushが失敗した場合、作成済みのローカルcommitは残ることを表示し、自動pull、rebase、force pushは行わない。
- 実行前に、現在のブランチにupstreamが設定済みであり、Git競合がないことを検証する。
- 確認ダイアログに変更ファイル一覧とcommit messageを表示し、利用者が確認した全変更だけをステージする。
- commit messageは操作内容から決定的に生成し、pushは通常の `git push` のみとする。push拒否時はcommitをローカルに残して案内し、pull / rebase / force pushを自動実行しない。
- PoCでは `main` を直接共有ブランチとして使い、ブランチ作成・PRレビューの仕組みは導入しない。`git pull` 後に編集し、利用者が内容と `git status` を確認してから手動で `git add`、`git commit`、`git push` を実行する。Git競合の解消は利用者が行い、アプリは競合状態の検知と案内までを担う。
- Gitリモートの選定・アクセス権設定はチームの既存基盤に委ね、リポジトリ内にトークンやURLを固定しない。

## 3. 楽観ロックによる競合防止

- Task取得APIは本文・Front Matterとともに、ファイル内容から計算したrevision（SHA-256等）を返す。
- 詳細保存とstatus更新は、読み込み時のrevisionを送る仕様に変更する。
- サーバーは保存直前のrevisionと比較し、不一致ならHTTP 409を返す。ファイルを上書きしない。
- UIは「別の変更があります。再読込して差分を確認してください」と表示し、ユーザーが再読込または手動マージを選べるようにする。
- Drag & Dropも同じrevision検証を通し、失敗時はカード位置を戻す。
- 原子的な一時ファイル書き込みとrenameを用い、書き込み途中のMarkdownを読まないようにする。

## 4. Task ID採番の共同運用

以下を調査・決定した上で実装する。既存の `EPF-0000` 形式を無断で変更しない。

- 案A: `tasks/sequence.md` をMarkdownの正本として追加し、採番更新もGitレビュー対象にする。
- 案B: Taskを一意な仮IDで作成し、`main` へpushする前に正式IDを割り当てる。
- 案C: メンバーまたはブランチに採番範囲を割り当てる。

推奨は案Aである。ファイルはDBではなくMarkdownであり、採番の意図・最終採番値・更新規則を追跡できる。一方で同時作成時はGit競合が起こり得るため、作成前のpullと`main`へpushする前の再採番手順を自動検証・運用ガイドの両方で支える。

## 5. 再読込と派生View

- UIに「リポジトリ更新を反映」操作を追加し、Task一覧・Git状態・WBSの生成時刻を再取得する。
- ファイル監視は最初は任意のポーリングまたは明示的な更新操作に留める。ネットワークファイルシステム上の監視には依存しない。
- `views/wbs.md` は引き続き派生Viewであり、Task変更後またはpull後に再生成する。
- WBSの生成結果に元Taskのrevisionまたは生成元commitを記録し、古いViewを識別できるようにする。
- 現在のWBSは `views/wbs.md` をエディタで開いて確認する。UI内プレビューはこのPlanの必須範囲に含めず、必要性を利用後に判断する。

## 6. AI利用の安全性と可観測性

- Chat UIにAdapter種別（Codex / Mock）、CLI解決結果、フォールバック理由を表示する。
- Codexは引き続きread-onlyで分析し、アプリが検証した操作だけをMarkdownへ反映する。
- AIが作成するTaskにもrevision・採番・必須Front Matter検証を適用する。
- AI提案の内容と実際に適用した操作を画面上で区別する。
- チーム内の会話やMarkdownを外部へ送る可否は、各メンバーのCodex利用ポリシーに従う。リポジトリ側で認証情報やプロンプトログを収集しない。

## 7. Markdown品質とCI

- `npm test` に加え、全Taskの必須Front Matter、ID重複、status / priority値、Requirement参照、UTF-8を検証するコマンドを追加する。
- GitHub Actions等のCIを採用するかはGitホスティング基盤に合わせて決定する。採用時も検証のみとし、Markdownを自動変更しない。
- WBSをCIで検証する場合は、生成差分を失敗として報告し、CIがcommitしない運用にする。

# 実装ステップ

1. チームのGitホスティング、`main` へ直接pushする運用、対象人数、同時編集頻度、Codex利用ポリシーを確認する。
2. `tasks/sequence.md` を使う採番方式のADRを作成し、既存Taskとの整合性と競合時の手順を決定する。
3. Markdown Reader / Writerにrevision算出、条件付き更新、原子的書き込みを実装し、409エラー形式を定義する。
4. Task詳細編集とDrag & Dropにrevisionを渡し、競合UI・再読込操作・失敗時の復元を実装する。
5. Task作成とAI作成に共同採番・保存検証を適用する。
6. Git状態表示を拡張し、ahead / behind、未追跡、競合中、WBSの鮮度を表示する。
7. ヘッダーに Pull を追加し、作業ツリー確認、git pull --ff-only、状態表示、成功後の再読込を実装する。
8. Git状態パネルに変更一覧・commit messageを確認できる `Commit & Push` 操作を追加し、明示承認後のステージ、commit、通常push、失敗時の案内を実装する。
9. Adapter診断とMockフォールバック表示を改善し、各自のローカルCodex設定を尊重する。
10. チーム導入ガイド、`.env.example`、Git運用ガイド、競合解決手順を追加する。
11. Markdown検証コマンドと必要に応じたCIを追加する。
12. 2名以上・別cloneでの作成、同一Task編集、Pull後の更新、Codex未設定、競合解消、明示承認付きcommit / pushの受入テストを行う。

# 受入テスト

- メンバーAとBが別cloneで起動でき、同じリモートへ別Taskを安全に反映できる。
- 両者が同じTaskを編集すると、後から保存する側は409を受け、既存変更を上書きしない。
- Task作成時にID重複が検出され、修正手順が案内される。
- pull後に再読込するとKanbanとGit状態が一致する。
- Pull は未コミット変更または履歴分岐時に止まり、自動マージを行わない。早送り更新の成功時だけTask一覧とGit状態を再読込する。
- 利用者が `Commit & Push` を押した場合だけ、確認ダイアログに表示した変更を含むcommitが現在のupstreamへpushされる。
- upstream未設定、push拒否、Git競合がある場合はcommit / pushせず、理由と次の手順を表示する。
- 実行中、成功、失敗の状態が画面で区別でき、実行中に二重操作できない。
- Codex利用可能なメンバーはCodex、利用不可なメンバーはMockで起動できる。
- リポジトリに秘密情報、Codex認証情報、一時出力が追加されない。
- WBSがTask正本から再生成され、手編集を前提にしない。

# リスクと軽減策

| リスク | 軽減策 |
|---|---|
| 同一Markdownの同時編集で内容を失う | revisionによる409、原子的書き込み、再読込と手動マージ導線 |
| 同時Task作成でIDが衝突する | 採番方式をADRで確定、CI検証、push前の再採番手順 |
| 各PCのCodex環境差 | Adapter診断、`CODEX_CLI_PATH`、Mockフォールバック、導入ガイド |
| LAN公開で認証なしアクセスが発生する | localhost bindを既定として維持。公開は別フェーズで認証から設計 |
| WBSがTaskより古くなる | 生成元情報、鮮度表示、commit前の再生成チェック |
| Git操作に不慣れなメンバーが競合する | 最小フロー、画面上の状態案内、競合解決手順、レビュー |
| 変更を確認せず共有してしまう | 自動pushは禁止し、変更ファイルとcommit messageを表示した明示承認操作だけを提供 |
| 意図しない変更がcommitに混入する | 確認ダイアログで全変更を表示し、利用者の承認なしにステージしない |`


# レビューで決める事項

1. チーム共有は第一候補の「各自のclone + Gitリモート」で進めてよいか。共有ホスト型を必要とするか。
2. Gitホスティング基盤と、`main` へ直接pushする利用者・タイミングをどう決めるか。
3. Task ID採番は案A（`tasks/sequence.md`）でよいか。ID形式を維持するか。
4. 想定チーム人数と、同一Taskを同時に編集する頻度。
5. CIを導入できる基盤と、必要な必須チェック。
6. Codex利用を任意とするか、チーム共通の利用ガイドを設けるか。
7. 任意の変更後に使える明示承認付き `Commit & Push` を採用してよいか。確認粒度とcommit message形式をどうするか。

# 実装しないことの再確認

このPlanのレビュー・承認前には、共有サーバー、認証、DB、Git自動操作、Task採番方式の変更、既存Markdownの変換を実装しない。
