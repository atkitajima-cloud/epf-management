# 背景

`epf-project`にGit remoteがなく、`epf-backend`にも未pushのcommitがある。共有・復元経路を確認できない状態では、本番開発メンバーが同じ基準版を取得できない。

# 目的

`epf-project`、`epf-management`、`epf-backend`、`epf-frontend`の正本と履歴の共有先、バックアップ、復元手順を明確にし、ローカル作業ツリーを失っても指定した版を取得できる状態にする。

# 完了条件

- [x] ExecPlanを作成し、人間レビューで実装範囲と検証方法を確認できる状態にする。
- [ ] 人間がExecPlanの実施範囲と検証方法を承認する。承認前に実施した操作の扱いも決める。
- [ ] `epf-project`の仕様・設計・ExecPlan、`epf-management`のRequirement・Task・Skill、`epf-backend`の実装・運用手順、`epf-frontend`の実装・運用手順について、各CodeCommit repoの`main`にある基準commitと取得先を記録する。
- [ ] 4 repoのCodeCommitから取得するためのprincipalと読み取り権限、認証情報を置かずに利用する手順を記録する。
- [ ] `epf-backend`のローカル先行6 commitについて、Pull Requestの人間レビュー後に`main`へ反映するか、反映しない理由を記録し、共有先とローカルの差分を解消する。
- [ ] 4 repoのCodeCommit `main`を一時的な空ディレクトリへ取得し、記録したcommitと主要な正本ファイルの一致を確認する。既存のローカル履歴や未pushファイルに依存せず復元できることを確かめるためであり、別端末は必須としない。
- [ ] 4 repoのバックアップの保管先・更新方法・アクセス権と、CodeCommitから取得できない場合の復元手順を記録し、実際に復元してcommitを照合する。
- [x] AWSアカウント`259183055835`の`ap-northeast-1`で、`epf-poc-project`と`epf-poc-management`のCodeCommit repo作成に成功したことを記録する。既存の`epf-poc-backend`と`epf-poc-frontend`も確認した。
